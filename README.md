# tiny-api-agent

Training a small language model with GRPO to call APIs it has never seen, from documentation that may be wrong.

> Design stage. No code yet; this README is the plan.

## The idea

Clean, single-turn tool calling is well studied. Give a model a well-formed function schema and it will usually emit a correct call, and [ToolRL](https://arxiv.org/abs/2504.13958) showed that GRPO with a decomposed reward improves small models substantially on held-out tools.

What is not solved, at small scale, is the version that actually happens in production:

- the spec the model is given has drifted from what the server enforces
- the server answers with a 400, sometimes helpful, sometimes a bare status code
- the model has to notice, repair, and finish in a small number of requests

This project trains a 1.5B to 3B model to do that. The model is the **executor** in a two-model system: a larger orchestrator picks which API to use, and hands this model one API's full spec plus a short task instruction. The executor owns the HTTP loop end to end and returns a small structured result.

The training signal is execution-grounded. Nothing is compared to a reference trajectory; the reward is whether the mock server ended up in the right state, minus a cost per request.

## What the executor sees and returns

**Input**

- a task instruction, phrased the way an orchestrator would phrase it (terse, occasionally underspecified)
- the full spec of **one** API, all endpoints, in some documentation format
- auth context and any identifiers already resolved upstream

**Behavior**

- makes HTTP requests against the API, reads responses, repairs on errors
- stops when done or when it hits a hard request budget
- never sees other APIs in the same episode

**Output**

A tiny fixed schema:

```json
{ "ok": true,  "data": { ... } }
{ "ok": false, "reason": "spec has no endpoint that can do this" }
```

The `data` field is the response of the final call, passed through untouched. For a task that needs more than one call (a lookup, then a write), the final write's response is what comes back. The `reason` field is what lets the orchestrator recover when the executor cannot.

## The two difficulty axes

Everything interesting in this project is controlled by two knobs.

**Spec drift.** How wrong the documentation is relative to the live server. Drift types are applied programmatically to a true schema, so the rate and mix are controllable and whole drift patterns can be held out:

- parameter renamed (`book_id` in docs, `bookId` on the server)
- optional parameter is actually required
- endpoint moved (new path, new version prefix)
- enum gained or lost a value
- auth requirement enforced but absent from the docs
- example in the docs omits a required field

**Error verbosity.** How much the server tells the model when a request fails. Ranges from Stripe-grade error bodies that name the missing field and allowed values, down to a bare `400` with no body.

Zero drift with maximum verbosity is ordinary clean tool calling, which is the first curriculum stage and a baseline, not the goal. High drift with a bare `400` is the hard regime.

## Components

Six pieces. Two of them are most of the work.

| Piece | What it does | Effort |
|---|---|---|
| **Task and spec generator** | Produces episodes: a synthetic API with its true schema, a drifted spec to show the model, an orchestrator-style instruction, and the expected end state. Enforces held-out API families and held-out drift patterns. | Large |
| **Environment** | One generic mock server driven by any true schema. Strict validation, per-episode state, configurable error verbosity. Resettable and fast. | Large |
| **Rollout harness** | Runs one episode: builds the prompt, parses model output into a request, sends it, appends the response, loops until done or out of budget. Records which tokens were model-generated so server responses are masked from the loss. | Medium |
| **Reward function** | Reads final server state and the model's structured output, returns a scalar. Cheap and hard to game. | Small |
| **Trainer** | GRPO with LoRA. TRL to start, verl if multi-turn rollouts outgrow it. | Small |
| **Evaluation suite** | Held-out APIs, success rate broken out by drift level and error verbosity, for the base model, the trained model, and a frontier model. Built before training starts. | Medium |

### How the generator works

The structure is code; the content is randomized and partly generated by a frontier model. Nothing is hand-written per API.

- A small grammar defines what an API can be: resources with typed fields, operations, parameter locations, nested bodies, list params, pagination, enums, operations that depend on a previous call's result. A fake API is a random draw from this grammar.
- A frontier model supplies domain vocabulary (realistic names for a "veterinary clinic API"), renders the schema into documentation in varied styles, and writes task instructions in several phrasings. Generated once, offline, cached.
- Drift transformations are small functions from true schema to corrupted copy plus a record of what changed.
- Expected end state is derived deterministically from the true schema and the target operation.

The grammar must be wider than it feels necessary. If every API is CRUD on three resources, the model learns the grammar instead of the skill.

## Reward

Starting point:

- full credit if the final server state matches the expected end state, the returned `data` matches the expected response, and the structured output is well-formed. The `data` check is what makes read-only tasks gradable; a GET changes no state.
- per-request penalty, so a correct call in one request beats a correct call in four
- small shaping term for reaching the right endpoint, to keep early training from being all zeros
- for no-fit episodes (5 to 10 percent of training), credit for returning `ok: false` with no mutating calls made
- zero credit for `ok: false` on a task the spec could do, so giving up is never the easy way out

Open question this project should answer: ToolRL argues dense decomposed rewards beat binary; [MUA-RL](https://arxiv.org/abs/2508.18669) argues dense rewards discourage exploration after errors in multi-turn settings. Run both on the same environment and report.

## Training plan

1. **Measure the base model first.** Success rate per drift level and error verbosity, no training. Decides whether cold-start GRPO is viable or whether an SFT warmup is needed.
2. **Cold-start GRPO on clean specs.** ToolRL found cold-start beat SFT-then-GRPO on held-out tools; default to no SFT.
3. **Curriculum on drift.** Increase drift rate and reduce error verbosity as success rate rises. The model's own improving policy does the warmup.
4. **Fallback if a stage sits at zero reward:** a small SFT set of repair trajectories, distilled from a frontier model against the mock server.
5. **Evaluate on held-out API families and held-out drift patterns**, plus a handful of real public APIs with permissive specs to check the synthetic-to-real gap.

Base model: Qwen2.5 or Qwen3 instruct at 1.5B to 3B. LoRA or QLoRA, single GPU.

## Design decisions already made

- One API per episode. Distractor endpoints within the API, never multiple APIs in one prompt.
- The spec is always present. No "explore from a bare URL" setting; without a spec the parameter namespace is unbounded and the model would only learn a prior over developer naming habits.
- The format of the spec is irrelevant. What matters is the gap between what the model is told and what the server enforces.
- Training environment and deployment contract are identical. Nothing in training gives the model information it would not have in production.
- Hold out whole API families and whole drift patterns, not individual endpoints.

## Where this is useful and where it is not

A frontier model with the spec in its prompt will do a single clean call better than this will. The case for a small trained executor is narrower:

- agents that make dozens of API calls per task, where a frontier model per call is too slow and expensive
- specs that cannot leave the building, or deployments with no network
- reliability after an error, which is where small base models fall apart and prompting does not fix
- as the executor half of an orchestrator/executor split

It is not useful for one-off integrations or for deciding which API to call at all.
